01 / The claim

Governance is speed. Chaos invoices later.

The usual story is that process slows delivery down. My experience running a multi-account portfolio says the opposite: ungoverned delivery is the slow kind — it just hides the cost until later.

Ungoverned

Fast today, paid for later

Every problem is solved from scratch, by whoever is closest. The fix lives in someone’s memory. The same failure returns next month and costs the same hours again — plus whatever it cost the client the first time.

Governed

Paid once, then free

The failure is written down, turned into a rule, and the rule is enforced. The next time the same situation appears, the rule handles it. The cost of the lesson is paid exactly once.

Solving the same problem twice is the actual waste.

Not process. Not documentation. Repetition.

02 / The mechanism

Failure in. Rule out.

Each failure goes through the same four steps. The retrospective is not the output — the enforced rule is.

Incident→ Written retrospective→ Standing rule→ Enforced check

A retrospective that ends in feelings is a meeting. It produces agreement, maybe an apology, and no change in what happens next time. A retrospective that ends in a written, enforced rule is an asset: it keeps paying out every time the situation recurs.

Across the portfolio that meant more than 16 written retrospectives, each one converting a single defect into a standing control. Over one quarter the same habit produced roughly 30 automation scripts and 8 SOPs — not because anyone loves process, but because each of them replaced a problem we had already solved once by hand.

03 / In practice

Four failures. Four rules.

One quarter, four retrospectives, one pattern: every failure was a missing rule, and every fix was a written one.

  1. Failure

    A client status report with roughly 10 of 13 items wrong — status inferred from who emailed last, not the tracker.

    →

    Rule

    Inference banned from status reporting. Ground truth first, or the item ships labelled “unverified”.

  2. Failure

    An investigation framed the wrong way round, so a surprising finding nearly went out unchallenged.

    →

    Rule

    A mandatory adversarial re-read before any surprising finding ships.

  3. Failure

    Project boards that looked empty, so nobody could see what was actually in flight.

    →

    Rule

    An intake SOP: every request lands on a board through one door.

  4. Failure

    Reconciliation chaos between documents, trackers and boards that each told a different story.

    →

    Rule

    A document → sheet → board procedure with sign-off on every row.

04 / The judgement trap

Checklists trust you. That’s the flaw.

The most useful finding from the retrospectives: a rule whose trigger is your own judgement cannot catch an error in that judgement.

A checklist only runs when someone decides it applies. The failures worth preventing are exactly the ones where that decision is wrong — the report that felt done, the board that looked neglected. So the strongest rules don’t wait to be remembered. They sit in the path of the work as a hook or a preflight and run every time.

MemoryRuns if someone remembers
ChecklistRuns if someone decides it applies
TemplateShapes the work, can be skipped
Preflight / hookRuns every time, in the path

Conceptual ordering, not a measurement

Preflight

The board that wasn’t neglected

A board-visibility check found that boards were silently hiding tickets created through the API: 60.5% hidden on one board, 100% on another, 40 of 48 on a third. It read exactly like a neglected board, and it was not. Judgement would have blamed the team; the preflight found the system.

Gate

The email that checks itself

After a real defect reached a client, outgoing client email gained a mechanical pre-send check: two different dates for one deliverable, internal details leaking out, completion claims without evidence. It doesn’t rely on the sender noticing — that was the original failure.

Precision about what you don’t know is a feature.

05 / Ground truth or nothing

“Probably done” is fiction.

The most dangerous words in delivery reporting are “it’s probably done”. A report becomes fiction one reasonable guess at a time.

The rule after the wrong report was simple: no inferred values in anything a client sees. Every status traces to an authoritative source — the tracker, the board, the artifact — or it ships labelled “unverified”.

It feels slower. It is faster. The hours that used to go into unwinding confidently wrong reports now go into the work. And “unverified, checking” turns out to build more trust with a client than a clean-looking report that is quietly made of guesses.

06 / The limits

Rules ossify. Prune them.

A rulebook is not free. Written honestly, the habit has three costs worth managing.

  1. 01

    Rules outlive their reasons.

    A rule written for one failure keeps running after the system that caused it has changed. Each rule needs its origin written next to it, so it can be retired when the reason is gone.

  2. 02

    Rules don’t cover the new problem.

    Rules encode past failures. A genuinely new situation still needs judgement — the rulebook only frees attention for it by handling the repeats.

  3. 03

    Process for its own sake is the same waste.

    A rule that never fires, or that people route around, costs effort and earns nothing. If a failure hasn’t recurred and the check only adds friction, delete it.

A retro that ends in feelings is a meeting. One that ends in a written rule is an asset.

Culture is just the rules you actually enforce.
