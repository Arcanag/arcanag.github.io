01 / The problem

PM overhead scales with team size.

Parsing requirements is mechanical. Assigning work is a lookup. Status reports are aggregation. None of it needs human judgment.

04 / The six agents

Six agents. One job each.

Unstructured → structured

Requirement Parser

Turns email, Slack and notes into requirements with priority and acceptance criteria — and asks the missing questions.

Requirement → task

Decomposition

A 4-level work breakdown. Stories failing INVEST checks are flagged with reasons, not silently accepted.

Tasks → RACI

Routing

Weighs expertise, capacity and dependencies. Flags key-person risk.

State → status report

Communication

Aggregates progress, blockers and milestones into client-ready reports.

Question → answer

Chat

“What’s blocking the payment integration?” — answered from live data.

Graph → P50 / P75 / P90

Timeline

07 / Honest assessment

Where it falls short.

  1. 01

    Linear orchestration

    A timeline change should trigger re-routing and an updated report. That feedback loop doesn’t exist yet.

  2. 02

    LLM output consistency

    Decomposition sometimes produces stories that are too large or vague; INVEST checks catch some, not intent drift.

  3. 03

    No production deployment

    Runs locally — no CI/CD, staging or monitoring.

  4. 04

    Unvalidated Monte Carlo

    Parameters come from industry heuristics, not calibrated against real outcomes.

  5. 05

    Multi-channel intake is an MVP

    Signal-to-noise filtering is basic; a busy channel would surface too many false positives.

Without real project data, this is a well-architected demo.

The path to product: deploy with a real team, measure outcomes, iterate on prompts from PM feedback.

09 / In hindsight

Five things I learned.

  1. 01

    Multi-agent design is a product problem

    How many agents, and where each boundary sits, are product decomposition questions disguised as architecture.

  2. 02

    The schema is the product

    More time went into the data model than any single agent. It defines what the product can and cannot do.

  3. 03

    Testing AI needs a different strategy

    You can’t assert on exact LLM output, so tests check structure, required fields and constraints.

  4. 04

    Protect user credentials

    All AI calls go through a server-side proxy, so keys are never exposed in the browser.

  5. 05

    Speed comes from experience

    Years of delivering AI products made it possible to move fast without skipping fundamentals.

The human’s role shifts from implementation to product judgment.
